# The local site — specification

Normative spec for `tools/serve-site.py` and `tools/build-card-index.py`. Self-contained:
an agent with no prior context can rebuild, verify and extend the site from this document.

The generated output was already a website's worth of pages — 19 sector profiles, 386 event
cards, a chooser — but it had no addresses. A page was `sectors/sector-rock-homeworlds.html`
on disk, or a slug inside the save watcher's iframe, and the 386 cards had no index at all.
This turns the same files into a site you can navigate, link to, and hand somebody a URL for.

```
sectors/index.html            ──►  /sectors/            the chooser, ?pick= selects
sectors/sector-<slug>.html    ──►  /sectors/<slug>      one profile, ?seen= + ?beacons=
cards/index.html              ──►  /cards/              the event index, ?q= ?sector= ?tag=
cards/card-<slug>.html        ──►  /cards/<slug>        one card
                                   /                    home  (the server's own page)
```

---

## 1. Running it

```bash
python tools/serve-site.py                  # http://127.0.0.1:8080
python tools/serve-site.py --open           # ...and open a browser at it
python tools/serve-site.py --check          # walk every route + asset, exit non-zero
python tools/serve-site.py --routes         # print the route table
python tools/build-card-index.py            # → cards/index.html
python tools/build-card-index.py --verify   # check the built index
```

### If you are an agent launching this

**`serve-site.py` without `--check` or `--routes` is a server that never returns.** Launch
it with Bash `run_in_background: true`. A foreground call blocks until the tool times out
and tells you nothing.

`--check` is the pre-flight: it resolves all 418 routes and every relative asset those pages
ask for, in-process, and prints a count. It starts nothing. Run it before serving and after
any change to the build.

`--port` if 8080 is taken. To stop it, kill what is listening on the port — not `pkill`
(absent from this machine's Git Bash) and not by matching `python.exe` (the interpreter here
is `python3.10.exe`):

```powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen |
    ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

**Python reads the source once, at import.** An edit to `serve-site.py` never reaches a
server that is already up — restart it. Content is different: pages are read from disk per
request, so rebuilding a card or an index shows up on the next reload with no restart.

### It is a second server, beside the watcher

| | port | serves | why |
|---|---|---|---|
| `serve-site.py` | 8080 | the site: wrapped pages, nav, clean URLs | a person navigating |
| `save-watch.py` | 8787 | one shell whose iframe swaps to the current event | a game in progress |

**The watcher serves no pages at all** — it computes a site URL, publishes it as `url` in
`/current`, and its shell points an iframe at `site + url`. Its old page routes 302 here.
So this server is where every page comes from, and the watcher is a client of it
(`SAVE-WATCH.md` §5a).

They remain two processes on two ports, deliberately: the watcher's shell is a frame that
repaints twice a second and wants no chrome, and the watcher's real job — reading a save and a
log — has nothing to do with serving files. `--site` on the watcher points it at a hosted copy,
which is the whole reason the URL carries the state.

## 2. The route table

`resolve(path, query) -> Response` is the whole table, as one pure function. `--check` calls
it directly, so the checker exercises exactly what a browser gets rather than a second
implementation of the same rules.

| Route | Serves | Notes |
|---|---|---|
| `/` | the home page | generated by the server, §4 |
| `/sectors/` | `sectors/index.html` | full document, chrome spliced in |
| `/sectors/<slug>` | `sectors/sector-<slug>.html` | fragment, wrapped |
| `/cards/` | `cards/index.html` | full document, chrome spliced in |
| `/cards/<slug>` | `cards/card-<slug>.html` | fragment, wrapped |
| `<page>?raw=1` | the built file, `text/plain` | §6 |
| `/sectors/<slug>?seen=` `?beacons=` | the same profile, marked up for a run | §5c |
| `/sectors/...`, `/cards/...` | any other file on disk | the card runtime, payloads, profile JSON |

Redirects, all `301`, query string preserved:

| From | To | Who asks for it |
|---|---|---|
| `/sectors`, `/cards` | `…/` | a person typing |
| `/sectors/index.html`, `/cards/index.html` | `…/` | the built pages, and old links |
| `/sectors/sector-<slug>.html` | `/sectors/<slug>` | the chooser's own card links |
| `/cards/card-<slug>.html` | `/cards/<slug>` | a sector profile's corner `↗` links |
| `/sector/<slug>`, `/card/<slug>` | the canonical form | the save watcher's route shapes |

The trailing slash on the two index routes is not cosmetic. From `/sectors`, the page's own
`href="sector-rock-homeworlds.html"` resolves to `/sector-rock-homeworlds.html` — one level
too high, and a 404 on every card in the grid.

## 3. Nothing is rewritten — and why that works

**The server edits no built file and rewrites no link.** Not restraint for its own sake: the
pages have to keep working off `file://` and keep publishing as artifacts (`SECTOR-PAGE.md`
§9, `EVENT-CARD.md` §5), so their links must stay relative and their bytes must stay what the
build wrote.

What makes that possible is a property of the URL scheme, and it is the load-bearing idea in
this file:

> **`/sectors/<slug>` has the same base path as `sectors/sector-<slug>.html` has on disk.**

So every relative reference in a built page resolves to a real route here, unchanged:

| In the page | From `/sectors/<slug>` | Served as |
|---|---|---|
| `../cards/card-x.html` | `/cards/card-x.html` | 301 → `/cards/x` |
| `../cards/runtime/card.js` | `/cards/runtime/card.js` | the file |
| `../cards/data/x.js` | `/cards/data/x.js` | the file |
| `sector-y.html` (from `/sectors/`) | `/sectors/sector-y.html` | 301 → `/sectors/y` |

The redirects upgrade in-page links **as they are followed**, which is what buys clean URLs
without touching the pages. The cost is one extra hop on a navigation, and none on an asset
load — the runtime and the payloads are served directly, because a redirect on a
`<script src>` would be paid on every box a reader opens.

**Keep the redirect rule narrow.** Only `card-<slug>.html` and `index.html` redirect under
`/cards/`; everything else there is a file. A rule that redirected all of `/cards/` would
break `runtime/card.js` and take the sector pages' in-place cards with it.

### Beacon boxes still open onto cards

A sector profile loads `cards/runtime/*.js` and `cards/data/<slug>.js` with a `<script>` tag
when a reader opens a beacon box (`SECTOR-PAGE.md` §6.1). Over http those resolve as above
and the box opens exactly as it does off disk — verified, not assumed (§7). This is the one
behaviour a published artifact cannot have, and the site keeps it.

## 4. The chrome

Cards and sector profiles are **fragments**: no `<!doctype>`, no `<html>`, no `<head>`,
because the Artifact publisher supplies the document. The server supplies it instead, and
that wrapper is the natural place for the nav — the built file stays untouched.

Two paths, because there are two shapes on disk:

- **`fragment_page()`** — cards and profiles. Builds the document around the fragment, and
  lifts the fragment's `<title>` into the head it is building.
- **`spliced_page()`** — the two indexes, which are already full documents. Extends the
  page's own `<head>`, inserts the bar after `<body>`, appends the theme script.

Four things are less obvious than they look:

- **The fragment's `<style>` stays in the body.** A `<style>` there is honoured by every
  browser, and hoisting it into the head would put the page's stylesheet *before* the
  chrome's instead of after it — quietly reversing which one wins wherever they collide.
- **Every chrome selector is prefixed `sb-`.** The pages define `.wrap`, `.card`, `.note`,
  `.chip` and `.name` in their own stylesheets, which load later in the document. A bare
  class name in the bar would be repainted by them.
- **The bar is `position: fixed`, not sticky.** The pages give `body` a padding, so a sticky
  element inside it is inset horizontally and resolves its containing block against whichever
  ancestor the page happens to have. The bar then reclaims its space with
  `body { padding-top: 3.5rem !important }` — by weight, not by matching each page's value,
  because a card's padding is `2.4rem` and a profile's is `2.6rem`.
- **The title is read past the comments.** Both shells open with a banner comment that
  contains the literal string `<title>` ("build-sector.py replaces the `<title>` line…"), so
  a plain search matches the comment and, with `DOTALL`, runs to the real closing tag — and
  the whole banner becomes the browser tab's name. `find_title()` blanks comments in a
  scratch copy of equal length first, so the offsets still index the original.

**Theme.** The bar carries a toggle that sets `data-theme` on `<html>` and remembers it in
`localStorage`; an inline script in the head applies it before first paint, so a remembered
theme does not arrive as a flash of the other one. No stored theme means no attribute, which
is the state the pages are built for — `prefers-color-scheme` decides. The first click picks
the opposite of what is on screen.

### The home page is chrome, not content

`/` is generated by the server, not built to disk. The boundary is worth stating because it
is the one place this could grow badly: **the build owns content, the server owns chrome.**
The home page is a front door — two doors with live counts and the 19 sectors as quick links,
earliest first. Nothing on it is a claim about the game that is not read from the profiles.

## 5. The two indexes

### 5a. The chooser — `sectors/index.html`

Built by `tools/build-sector-index.py`; `SECTOR-PAGE.md` §7b is its spec. What this file adds
is the query layer.

**The URL is the state.** `?pick=` seeds the page, and every pin writes it back with
`history.replaceState`, so the address bar always reproduces what is on screen and a
comparison is a link you can send. `localStorage` is the fallback for the **bare** URL only:
with a `pick` in hand, a remembered pin would silently rewrite what somebody deliberately
linked to.

Only a **hand** action is remembered. Seeding from `?pick=` never writes `localStorage` — the
save watcher opens this page at every sector choice (`SAVE-WATCH.md` §5d), and a reported
offer is not a preference.

| Param | Means |
|---|---|
| `?pick=a,b[,c,d]` | pin these into the comparison panel, in this order |
| `?column=1` | the picks are the next *column* of the map, not a verified reachable set — prints the caveat above the panel |

`?pick=` resolves each token independently, in this order, with case and all three word
separators (`-`, `_`, space) normalised away — so `ROCK_HOME`, `rock home` and `Rock-Home`
are one token:

1. exact slug — `rock-homeworlds`
2. exact game id — `ROCK_HOME`
3. exact display name — `Rock Homeworlds`
4. unique prefix of a slug or a name — `rock-home`
5. unique substring

**A token matching nothing, or more than one sector, resolves to nothing and the page says
so** — `picks_dropped` names the tokens it dropped. Naming a sector the caller did not mean
is worse than naming none, and the same rule already governs the watcher's own name
resolution. `rock` and `slug` are both genuinely ambiguous (two sectors each) and are
therefore dropped, not guessed: use `rock-home`, `rock-controlled`, `slug-home`.

Four tokens are accepted because the sector map can report a column of four. **Pinning by
hand caps at two** — what the map offers, and what a comparison is for — and a hand pin also
clears `column=1`, because the caveat is about an offer the map reported and a hand-picked
pair is no longer that offer.

### 5b. The event index — `cards/index.html`

Built by `tools/build-card-index.py`. One row per card: name, in-game id, derived tags, and
how many sector pools can place it. All 386, alphabetical.

Everything is read:

```
cards/trees/*.tree.json         slug, title, in-game id
extract-sector.Trees.profile    tags and blue options — derived from the tree
sectors/data/*.sector.json      which sector pools can place the event
```

**The tags come from `extract-sector.py`, not from the sector profiles.** The same
`Trees.profile()` the sector pages tag their pool rows with, called here on every tree. Two
consequences, and the second is the reason:

- a tag reads identically in both places, and cannot drift — the drift would be invisible,
  two plausible tag lists
- **the 118 cards in no sector pool are tagged too.** Reading tags back out of the profiles
  tagged only what a pool happens to list, which left a third of the index blank

**118 of the 386 sit in no sector pool** and say so with a `–` in the last column, rather
than being dropped. They are reachable another way — a chain step, a fight outcome, the boss
— and a list that quietly held 268 would read as the whole set. `?sector=none` is a filter
value like any other, because "no pool lists this" is an answer, not the absence of one.

50 rows carry no tags at all. That is honest: an empty beacon holds nothing to tag.

| Param | Means |
|---|---|
| `?q=` | substring of the name, the id, a tag label, a blue option, or a sector name |
| `?sector=<slug>` or `none` | only events that pool can place |
| `?tag=<tag>` | only events carrying that tag |

Same rule as the chooser: every filter is in the URL and typing writes it back. Nothing is
remembered anywhere else — a stored filter would hide events from the next reader of a
shared link.

**The last column counts pools, not beacons.** No file states how often an event is placed
(`SECTOR-PAGE.md` S4), and an event listed twice in one sector is one entry.

Two layout rules that were got wrong first:

- **Every column is a fixed width except the name.** Each row is its own grid, so an `auto`
  or `1fr` track is sized from *that row's* content and the columns come out ragged down the
  page — the ids wandered a hundred pixels because the row above held one chip and the row
  below held six.
- **The label row is `.row.head`, outside `.list`.** The filter selects `.list .row`, not
  `.row`: the label row is the same grid and therefore the same class, but carries no data
  attributes, so selecting it counted a 387th event and threw on the first keystroke.

### 5c. `?seen=` and `?beacons=` — this run's map, on a sector profile

Two parameters, both about the run in progress rather than the sector in general. `?seen=`
marks the events the run has been to; `?beacons=` says how big this map actually is.

```
/sectors/engi-controlled-sector?beacons=21&seen=engi-ship-attacked-by-mantis-ship,FREE_WEAPON
```

Either may appear alone. Neither present means **no markup at all** — the page is byte-for-byte
what it was before this existed.

#### `?beacons=<n>` — the count in the budget heading

```
BEACON BUDGET      21 placed this run · 14–32 slots allocated · 77 events in pool
```

First in the line, and the only bright figure in it, because it is the one fact about *this*
map — and it is what makes the allocated range mean anything: 14–32 slots against 21 placed
says most of the range was never reachable, which the range alone cannot say.

**It has to come from outside** — no file states it, because the map rolls the count. The save
cannot answer either: under Hyperspace it is read by content scan, which gives up the beacon
list entirely (`SAVE-WATCH.md` §3b). The **log** can, and the watcher now sends it: one
`Getting Event:` line per beacon the table filled (`SAVE-WATCH.md` §4d).

**"placed", not "beacons on the map", and the difference is real.** The count is beacons the
allocation table drew for. The entry beacon is the sector's fixed `<startEvent>` and the exit
is a fixed `FINISH_BEACON`, so neither is drawn — except in nebula sectors, where
`FINISH_BEACON_NEBULA` *is* in the list. That makes this exactly the figure to read the
budget's "N slots allocated" against, and a little short of the map's full beacon count. The
tooltip says so.

**The page reports it and derives nothing from it.** Which lines a short map cuts is a roll,
not an inference, and marking rows as cut would be exactly the guess the budget refuses to
make. A value that is not a positive integer is reported in the strip and otherwise ignored.

This replaced the `may be cut` chip, which is the better trade: a chip that fired on most lines
of most sectors, saying a line *might* be cut, against one number that says how much room there
actually was (`SECTOR-PAGE.md` §4.1b).

#### `?seen=<token>,…`

A `Seen` chip on every matching beacon box, and a count of them beside each budget line's name.

**The watcher owns this state, and the URL is its only channel.** That is a consequence of
the site being hostable: the watcher cannot serve the page, so the one thing it can still do
is decide what URL the browser is on. `?pick=` already works that way (§5a), and this is the
same channel carrying a bigger payload — which costs nothing measurable:

> **Where the values come from** is `SAVE-WATCH.md` §4c, and this page does not repeat it. In
> one line: `Creating event:` lines in `FTL_HS.log` after the last `Sector:` line, filtered to
> that sector's pool. **This page never derives anything** — the URL is its whole input, and a
> token it cannot place is reported rather than guessed at. Anyone can type one of these URLs
> by hand and get exactly what the watcher would have produced.

| | |
|---|---|
| worst realistic payload | 24 slugs from `federation-space`, the largest pool — **775 chars**, 834 with the URL |
| parse + mark, measured on that page (144 boxes, 1,972 elements) | **0.00 ms** median, 0.30 ms max over 200 runs |
| same at 140 KB, 180× anything real | 0.90 ms median |
| binding limit if hosted | nginx / Apache default request line, **~8 KB** — ten times the payload |

Slugs, not a bitmap. A bitmap over the pool would be 16 base64 chars instead of 775, and
would silently re-interpret an old link as a different set of events the moment a sector is
rebuilt and its pool ordering shifts. 800 harmless bytes is the better trade.

**Scope it to one sector.** Per-sector is 834 chars. A parameter accumulating a whole run —
eight sectors — is 5,949, still under 8 KB but no longer comfortably, and it is the one shape
that could hit a default server limit on a hosted deployment.

#### A token is a slug or an in-game event id, optionally with a visit count

```
engi-ship-attacked-by-mantis-ship     the card slug
ROCK_CRYSTAL_BEACON                   the in-game id, which is what FTL_HS.log prints
rock_crystal_beacon                   same thing; case and -/_/space are normalised away
store-engi:3                          visited three times
store-engi,store-engi                 also two visits — repeats accumulate
```

**Two forms for the count, because two callers want different things.** Repeats are the plain
form; `:n` is for a compacted or hand-written URL. Every token is a visit record, so the forms
add: `store-engi:2,STORE_ENGI` is three visits.

**A count means distinct beacons, not arrivals** — that is the watcher's contract, not this
page's. Flying back to a beacon fires its event again and must not count twice, while two
different beacons holding the same event must (`SAVE-WATCH.md` §4c). This page counts what it
is given; it has no way to know which beacon anything came from.

The URL bound does not change. A run visits at most 24 beacons, so there are at most 24 tokens
either way, and §5c's 775-character worst case still holds.

`:0` is **not** an error — it says the beacon was visited zero times, which is what saying
nothing says, so the token drops and nothing is marked or reported. A count that is not a
number **is** an error, and is reported as a count problem rather than as "not in this
sector's pool": `FREE_WEAPON:tow` names an event that is in the pool twice over, and blaming
the pool for it would send a reader looking in the wrong place.

Accepting ids is not a convenience. The watcher's own source is `Creating event: <ID>` in
`FTL_HS.log`, so the id is the currency it holds; requiring slugs would put a translation
table between the two.

One flat lookup is safe here, and that was measured rather than assumed: across all 386
cards, **no normalised event id equals a different event's slug**, so a token cannot name one
event and match another. (Ids are `UPPER_SNAKE` and slugs are `lower-hyphen`, which is why,
but the check is what makes it a fact.)

**A token that matches nothing is reported, never guessed** — the strip under the nav bar says
how many events were marked and lists what did not land. It says *"not in this sector's pool"*
rather than *"unknown"*, because that is all the page can honestly claim: it holds one
sector's events and nothing wider, so a real event from a different sector and a typo look
identical to it.

#### What it touches, and what it must not

- **A green `Seen` chip goes inline in the box's own `.t`** — immediately after the event
  name, which is the line a reader scans — reading `Seen 3` where the beacon was visited more
  than once, and plain `Seen` for the ordinary single visit, since a repeat is the only part
  that is news. Beside it, a green `n seen` chip in the budget row's own `.name`, **summing
  visits rather than counting events**: a store seen twice spends two of that line's beacons,
  which is what the budget is measuring. One colour for one idea, at both scales.
  Both inherit the page's existing `.tg` /
  `.mark` styling, so they look native, and neither adds a grid child — `.brow` is a
  five-column grid and a sixth cell would shift the pips and the count. **The pips and the
  count are never modified**, only added beside.
  Two things the chip has to override: `.t` is `font-weight: 500`, which the chip would
  inherit and render heavier than the same chip elsewhere; and it sets its own `color`, so it
  stays green through `.evbox:hover .t`, which repaints the name cyan.
- **Every box has a `.t`, whether or not it has any tags** — which is why the name is the
  right host. The tags row has to be created for a tagless event; the name never does.
- **Overlap is intended, and a cyan `n overlap` chip says how much of it there is.**
  `engi-ship-attacked-by-mantis-ship` is in both `DISTRESS_BEACON_ENGI` and `NEUTRAL_ENGI`,
  so one visit counts in both lines. 58 (sector, event) pairs land in more than one line
  across the 19 sectors; 12 sectors have none. Attributing a visit to one line would require
  knowing which beacon it was, which the URL does not carry — so both are counted, and the
  chip makes the double-counting legible instead of leaving the per-line totals quietly
  summing past the number of beacons actually visited. It counts **the visits on this line that
  are also counted on another line** — visits, so both chips are in the same unit and the
  arithmetic closes — and its tooltip names those lines.
- **A box's lookup keys are deduplicated before its count is summed.** A box offers its slug
  and its normalised in-game id, and for plenty of events those are the *same string*:
  `store-engi` and `STORE_ENGI` both normalise to `store-engi`. Summing over the raw key list
  added that event's visits twice, so `store-engi:2` rendered as `Seen 4`.
  Cyan is also `.mark.first`'s colour ("placed first"). They only ever meet on line one and
  read differently by text — which is why the two count chips carry their own classes rather
  than reusing it.
- **Lines are identified by index, never by label.** Two entries in one allocation table can
  carry the same list name, and keying the overlap map by label would merge them.
- **The line's own name is read before any chip is appended.** `.name` is where the chips go
  and it already holds `placed first` / `fill-in` chips as element children, so the label is
  taken from its text nodes only — `textContent` glues the chip words onto the list name.
- **The row count reads `.bpool > .pool`, direct children only.** An AE delta block sits in
  the same expansion with a `.pool` of its own; counting it would inflate a line with events
  the base list does not hold.
- **The strip counts events, not boxes.** An event reachable through both a budget line and a
  marker section has a box in each, so counting boxes reported ten for five events and read
  as though half the sector had been visited.
- **Events with no card are markable too.** They render as a plain `div.ev` with no
  `data-card`, but they still carry the in-game id in `.id`, and the run visited them either
  way.
- **No parameter, no markup.** Neither the style nor the script is attached when both
  `?seen=` and `?beacons=` are absent, so a plain sector page is byte-identical to what it
  was before this existed. `--check` asserts both directions (§7). A `?beacons=`-only URL
  also gets **no strip** — the count went into the heading, and an empty strip would still
  push the page down by its own height.

**It is injected by the server, never built into the page.** The overlay is chrome, on the
same boundary as the nav (§4) — so the built profile keeps opening off `file://` and keeps
publishing as an artifact, where a `?seen=` parameter means nothing and nothing is broken by
its absence.

Not done, and deliberately: `/cards/<slug>` on its own does not mark itself seen, and there is
no hand-ticking. Both are additive if wanted; neither is needed by the watcher.

## 6. `?raw=1` — the built file, as source

The nav's `Built file` link. It serves the file byte for byte as `text/plain`, so what the
build actually wrote is one click away from the page it produced.

It exists because the obvious version was wrong: a link to `/cards/card-x.html` redirects to
`/cards/x` and therefore navigates back to the page the reader is already on. A link that
looks like provenance and does nothing is worse than no link.

## 7. Verification

```bash
python tools/serve-site.py --check                                  # every route + asset
python tools/build-card-index.py --verify                           # the event index
python tools/build-sector-index.py --verify                         # the chooser
python tools/smoke-inline.py --all --base http://127.0.0.1:8080     # boxes open onto cards
```

`--check` walks every route in `routes()`, follows one redirect hop, and resolves every
relative asset each HTML response asks for **the way a browser will**: against the directory
of the URL the content actually came from. Two mistakes it is written to avoid, both of which
it made first:

- **Resolving assets against the pre-redirect path.** `/sectors` redirects to `/sectors/`; a
  checker that then resolved `sector-x.html` against `/` reported all 19 sector cards as
  missing, none of which reproduces in a browser.
- **A reference pattern loose enough to match JavaScript.** These pages build hrefs in
  script (`'sector-' + s.slug + '.html'`), so the pattern admits only what could be a path
  on disk. A checker that cries about `/sector-' + s.slug + '.html` trains a reader to
  ignore it.

`smoke-inline.py --base` runs the existing in-place-card checks against the served site
instead of `file://`. **Both modes are worth running:** a box reaches its card by a different
path in each — a sibling file on disk, a route on the server — and only the served one breaks
when the route table changes.

`--check` currently covers 418 routes: home, both indexes, 19 profiles, 386 cards, the two
runtime files, four `?raw=1` probes, the two directory redirects, and two `?seen=` probes —
one asserting the overlay attaches, one asserting it does **not** leak onto a page without
the parameter. The second direction matters as much as the first: an overlay that always
attached would be invisible until it collided with something.

## 8. Where fixes go

| Symptom | Fix in |
|---|---|
| a wrong URL, a missing redirect, a 404 | `resolve()` in `serve-site.py` |
| the bar, the wrapper, the theme, the home page | `NAV_CSS` / `document()` / `home_page()` |
| the `?seen=` marks, the count, the strip | `SEEN_CSS` / `SEEN_JS` in `serve-site.py` |
| wording anywhere in the chrome or the event index | `tools/site-vocab.json` |
| a tag label | `tools/sector-vocab.json` — shared with the sector pages, never duplicated |
| the event index's rows, columns or filters | `build-card-index.py`, then rebuild |
| a sector's own numbers or prose | the sector pipeline; this site only serves it |

**Never hand-edit `cards/index.html`.** It is build output, like every other page here.

The palette is sliced out of `tools/sector-page-render.html` between `TOKENS-START` and
`TOKENS-END` by three readers now — `build-sector-index.py`, `build-card-index.py` and
`serve-site.py`. The slice is duplicated; the palette is not. Adding a fourth reader is
fine; defining a colour anywhere else is not.

---

## 9. What is not handled

- **No search across event *text*.** The event index matches names, ids, tags, blue options
  and sector names — not the flavour text or the outcomes, which live in the trees and are
  not loaded by the index page.
- **No wiki layer.** `wiki/` is markdown and is not served. The site is the generated output
  only.
- **One reader assumed.** No caching headers, no compression, no concurrency limits beyond
  `ThreadingTCPServer`. It is a local site for one person on one machine.
- **The watcher is a client, not a merge.** It drives this site by URL and serves no pages
  itself (§1), but the two remain separate processes on separate ports, and the watcher's own
  shell has no chrome. Combining them is still not done, and still deliberate.
- **Review copies are reachable but not listed.** `/sectors/<slug>-review` serves a page
  `add-review-layer.py` produced, because the route checks the file; `routes()` skips them,
  because they are transient artifacts and not part of the site.

## 10. The hosted copy — `tools/build-pages.py`

The same site with the server taken out of it, for GitHub Pages:
<https://jparro00.github.io/ftl-wiki/>.

```bash
python tools/build-pages.py            # → site/  (gitignored), then checks it
python tools/build-pages.py --check    # check what is in site/, build nothing
python tools/build-pages.py --deploy   # ...and force-push site/ to the gh-pages branch
```

It **imports `serve-site.py` and calls its own `resolve()`, `fragment_page()` and
`home_page()`.** That is the whole design: the hosted pages *are* the local ones, rendered by
the same code, so the two cannot drift into two plausible sites. Nothing here re-implements
the chrome, and nothing here edits a built file — §3 still holds.

A static host cannot do three of the things §2–§6 rely on. Each has one replacement:

| The server does | Pages gets |
|---|---|
| `301` from `card-<slug>.html` to `/cards/<slug>` | the real page at `cards/<slug>.html`, and a **forwarding stub** at `cards/card-<slug>.html` |
| chrome links like `href="/sectors/"` | the same links, **relative** — `../sectors/index.html` |
| `?raw=1`, the built file as text | the nav's `Built file` points at the file on GitHub |

**The stub is the 301, without a server.** `location.replace(target + location.search)` —
`replace` so it leaves no back-button entry, and `location.search` because `?seen=` and
`?pick=` are the only channel the watcher has (§5c) and a redirect that dropped the query
would silently drop the run. A `<meta refresh>` sits behind it for a reader with JavaScript
off; that one does lose the query, which is the most a meta refresh can do. 405 stubs, ~350
bytes each.

**Relative, not root-absolute, and this is the failure that is invisible locally.** A project
Pages site is served from `/ftl-wiki/`, where `href="/sectors/"` is a 404 — but it works
perfectly on `127.0.0.1:8080`, so nothing local catches it. `build-pages.py` rewrites every
absolute URL the chrome emits against the page's own depth and **raises on one it has no
mapping for**, rather than passing it through to break only once hosted. The built pages
themselves contain no absolute URL at all, which is what makes the map closable; `--check`
asserts that no output page carries one.

**The `?seen=` overlay is attached to every sector page**, not only to the ones asking for it.
`SEEN_JS` already returns immediately when neither parameter is present (§5c), so the
behaviour is exactly the server's — what moves is where the decision is made. So
`save-watch.py --site https://jparro00.github.io/ftl-wiki` works — verified end to end, and
with no change to the watcher.

**It survives the `/ftl-wiki` path prefix because the watcher concatenates rather than
resolves.** `Watcher._url()` returns a path, `--site` keeps whatever string it was given,
and the shell composes `site + url`; a prefix on the origin is therefore carried, not
resolved away. This was first written up here as *not done, the watcher needs the prefix* —
which was an inference, and wrong. Two more things it depends on, both checked rather than
assumed: `github.io` sends no `X-Frame-Options` and no `frame-ancestors` CSP, so the shell's
iframe is allowed; and Pages tries the `.html` extension on an extensionless path, so
`/sectors/<slug>` reaches `sectors/<slug>.html` without the watcher knowing the export's
filenames.

Also written: `.nojekyll`, so Pages publishes the tree as built rather than running Jekyll
over it, and `404.html`, whose links are **absolute-with-prefix** — Pages serves that one file
for any missing path, so a relative link in it would resolve against whatever the reader
typed.

`cards/trees/` is not copied. The cards name it in a provenance comment and nothing fetches
it, and it is 5.8 MB of the 31.

### Verifying it

```bash
python tools/build-pages.py --check                     # every reference, every page
python tools/smoke-inline.py site/sectors/<slug>.html   # boxes still open onto cards
```

`--check` walks all 814 built files, resolves all ~4,500 relative references against the file
that makes them, and fails on a missing target or on any absolute URL. The in-place beacon
cards were verified in the exported tree over `file://` and against the hosted site, all 19
sectors — `../cards/runtime/card.js` and `../cards/data/<slug>.js` resolve in both exactly as
they do on disk, which is the point of keeping the directory shape.

> **`smoke-inline.py --all --base <hosted>` trips on the review copies.** `--all` globs
> `sector-*.html`, which picks up `sector-rock-homeworlds-review.html`; the local server
> happens to serve those because its route checks the file (§9), and the export deliberately
> does not carry them. Against a hosted base it 404s and the tool times out 30 seconds later
> with a traceback rather than a verdict. Name the pages instead, or use `--base` locally.

Two things that shipped wrong first, both invisible until the site was hosted:

- **The 404 page double-prefixed its own links.** Its body wrote `/ftl-wiki/sectors/…`, and
  the substitution that prefixes the chrome's links then prefixed those too. The body now
  writes the chrome's own `/sectors/` vocabulary and lets the one substitution handle both.
- **The second build could not clear `site/`.** `rmtree` stops on the deploy repo's read-only
  git objects, and stops *halfway*, leaving a partial site. `clear_output()` empties everything
  beside `.git` instead — which also keeps the deploy a one-commit force-push.

### What the hosted copy does not have

- **Clean URLs are `…/<slug>.html`, not `…/<slug>`.** GitHub Pages does try the `.html`
  extension for an extensionless path, so `/ftl-wiki/cards/ancient-device` also works — but
  nothing here depends on that, and every link written points at the explicit `.html`.
- **Latency and staleness, if the watcher points here.** Every swap is a round trip to
  GitHub rather than to localhost, and the pages are frozen at the last `--deploy`. Hosted
  is the right target for playing; local is the right target while rebuilding content.
- **One commit on `gh-pages`, force-pushed.** The build output is not history worth keeping,
  and a branch that accumulated it would grow by ~30 MB a deploy.
